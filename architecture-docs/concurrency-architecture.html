Noesis · target concurrency architecture · for approval

One server, many agents

Four things bound this system: how many searches run at once, how many connections exist, how many index runs are in flight, and how many processes hold a copy of the model. Today only the last one is even counted — and it is the expensive one.

Two of the assumptions behind the earlier plan turned out to be wrong when measured. Both corrections are below, and both change the design. Everything here ran on this machine against a live Qdrant 1.18.3 and a real model load.

01

Two corrections before the architecture

Both were my own assumptions; both were falsified
Correction 1 — client-per-thread was the wrong recommendation

I previously leaned toward one connection per worker thread. A bounded pool of 4 beats it, and beats today's unsafe code, on throughput, p95 and p99 simultaneously — because a bounded pool is also admission control. Capping concurrent queries stops Qdrant and the GIL thrashing, so latency stays flat as agents scale. Thread-per-agent is what produces a 1.2-second tail.

Correction 2 — the re-download you were worried about is not happening

Model weights are cached on disk once and shared by every process. Measured: first process 98.5 s (download + load), second process on the same cache 11.7 s with zero bytes fetched; four processes cold-starting simultaneously against one empty cache all succeeded, producing one shared cache. The repo already fixed the one real instance of this — the pre-M8 cwd-relative fastembed path, documented in default_fastembed_cache.

But the thing I expected to save you does not exist. I assumed weights would be mmap’d from that shared cache, so the OS page cache would share them across agents. Measured across two concurrent processes: Shared_File = 0 MB, private memory 976 MB each. The weights land in private tensors. Sharing the cache saves disk and download time; it saves no RAM at all.

So ten stdio agents is not ten downloads — it is roughly 11 GB of RAM and ten model loads. On a 16 GB laptop with the reranker on, that is the machine. No caching change fixes it. Only topology does.

02

The target architecture

Every boundary labelled with the number that bounds it

The organising idea: one process owns the expensive things, and every queue into them has a number on it. Today the model workers are bounded (one thread each, ADR-20) and nothing else is — searches land on CPython’s shared default executor, connections are a single shared object, and index runs are capped per project but not globally.

03

Search lane — why K slots and K connections

Scenario: bounded search + backpressure

The two numbers are deliberately the same number. If the executor admits K searches and the pool holds K connections, a connection is free whenever a thread is free — checkout never blocks and no lock is ever contended. One knob sets both, so they cannot drift apart.

Live server, 5,000 points, hybrid channel, prefetch 50. The same ordering holds at 8 and 16 concurrent searches; pool-of-4 p95 moves 15.9 → 16.4 → 16.1 ms across 8/16/32 agents, while every unpooled option degrades 2–5×. Zero errors and zero wrong results in every pooled run.

A lock still gets built, but as the correctness floor, not the mechanism: the :memory: configuration used by ~25 existing tests cannot have a second connection, because a second local client is a different database. The lock must be keyed to the client object so that when there is only one, the search path and the write path share one mutex rather than holding two different ones over the same state.

04

Index lane — the cap has to live in SQLite

Scenario: global cap on concurrent index runs

try_start_run already guarantees one run per project, and it does so across processes using BEGIN IMMEDIATE plus an owner-liveness probe. What it does not do is cap the total. Ten registered projects with auto_reindex on can start ten runs at once, all sharing one embedder worker, one index connection and the same executor.

The trap worth naming: an asyncio.Semaphore would look like a fix and would not be one. The deployment this repo documents runs an HTTP server and a stdio MCP process against the same database, so an in-process counter bounds one process while the other proceeds unaware. The cap belongs where the existing guard already lives.

05

Multi-agent — the cost is processes, not downloads

Scenario: many agents on one machine

What I have not resolved, and want your call on: how the shim finds its server. Simplest is that it refuses to start without one and says so. Most convenient is docker-style — probe the configured port, and spawn the server if nothing answers, which needs singleton election so ten agents starting together do not spawn ten servers. That is a real distributed-systems problem in miniature and I would rather not smuggle it in unnoticed.

Kept honest

The ~30 MB shim figure this section originally carried was an estimate, and it was wrong by about 5×. The shim now exists and measures 165 MB RSS / 133 MB PSS — fastmcp, httpx and pydantic are not free. The comparison still holds and is still the point (1427 MB per agent becomes 165 MB, so ten agents is roughly 3.1 GB rather than 13.4 GB), but it is a 4× saving, not the 8× the estimate implied.

Connection count corrected likewise: the wiring is K + 2, not K + 1 — a pool of K for queries, one for indexing, and one admin connection for the deletes, counts and scrolls that build no models.Document and must never take a query's slot.

The reranker is excluded throughout because it defaults to off; with reranker.enabled = true the per-process figure grows by roughly its 2.3 GB of weights, which I did not load.

06

Why this cannot silently come back

Scenario: CI guardrail — your “never again” requirement

Six review rounds passed over this. Worth being precise about why, because it tells you which layer to invest in: no test exercised readers alone, and the tests that did exist counted exceptions rather than checking results. The silent 99% was invisible to the oracle. A reviewer reading the diff could not see it either, because the class docstring claimed both paths were handled.

So three layers, each catching what the one before it misses:

  • Design — a raw client is not reachable from search code. Queries go through a checkout that hands back a connection; there is no shared object to touch. This is the only layer that makes the bug impossible rather than detectable.
  • CI grep — ci_greps.sh gains a pattern rejecting QdrantClient( outside runtime.py/prefetch.py and raw self._client use in the query path. Follows the file’s existing shape, including its convention of naming the review round that motivated each rule.
  • Tests with a real oracle — the default suite gets reader-vs-reader on one :memory: client asserting correct results; the -m server tier gets the same against a live server plus the latch check (run load, stop it, then verify quiet sequential queries are still correct). The server tier already runs in CI via the server-compat job, so no workflow edit is needed.

And one process point: the false claim in ADR row 76 — a measurement that does not reproduce — is itself the finding. Rule 9 exists for exactly this, and it earned lesson 20 another occurrence.

07

Open decisions

Everything else is settled; these change the diff

1. Does the thin shim ship in this PR, or become its own?

The shim is a new transport, not a bug fix. It has its own failure modes (server discovery, singleton election, what an agent sees when the server dies). My lean: this PR delivers the in-process architecture — search lane, index cap, guardrail, docs — and the shim lands next with its own ADR, because a shared server is only safe after the search lane is fixed. Shipping it here doubles a PR that is already six rounds deep.

2. K and Q — pick the numbers, or derive them?

My lean: [qdrant] query_connections = 4 as an explicit knob, with the queue depth derived from it rather than a second knob to get wrong. 4 measured best here on 4 CPUs; a machine with more cores may prefer more, and I would rather that be editable than inferred.

3. What does a rejected search return?

Under the bounded queue, overload has to surface. REST can answer 503 with a retry-after. MCP has no equivalent, so the choice is an error result the agent can read, or blocking until a slot frees. My lean: explicit error, because a silent stall is the failure mode this whole exercise is about.

Reproduction: probes and benchmarks are in the session scratchpad and can land in-tree with the PR if you want them committed. Docker, Qdrant 1.18.3, the 523 MB model cache and the full dependency set are live on this machine, so the -m server tier and the memory measurements can be re-run on demand.
