Noesis dashboard · issue #51 · model-prefetch progress

Polling vs. SSE, for one button

The "Download models" button needs a progress bar. Two ways to move that progress from the server to the browser — compared against what Noesis already does, not in the abstract.

Recommendation

Use polling.

Not because SSE is worse in general — because Noesis already has a live-progress mechanism, built for the index-run progress bars, and this job is small enough that reusing it costs nothing and building a second one buys nothing.

  • The dashboard already polls a JSON status endpoint every 2–8s for the index-run progress bar. This reuses that exact loop instead of adding a second, different one.
  • The download only has 4 checkpoints (grammars → tokenizer assets → model → reranker). SSE can't report progress any smoother than that — there's nothing finer-grained to push.
  • Zero new moving parts: no open connection to manage, no reconnect logic, no proxy-buffering edge cases.

How each one actually moves the bar

Same goal — the browser learns "grammars done, downloading the model now, 3 of 4 steps" — two different plumbing choices.

① Polling — chosen

Browser asks, server answers

The browser asks "how's it going?" every couple of seconds. The server just reads a status it's already keeping in memory and replies. No request is ever left open.

② SSE — not chosen

Server keeps a line open

The browser opens one connection and leaves it open. The server pushes an update down that same pipe the moment something changes, instead of waiting to be asked.

Side by side

Where they actually differ, for a local, single-operator admin control — not for a chat app or a stock ticker, which is the use case SSE is usually sold on.

Trait① Polling② SSE
New server code One plain JSON GET route. Same shape as the five other status endpoints the dashboard already has.Simpler A streaming response the connection stays inside of — a different code path from every other route in the app.
New client code One more branch in the polling loop that already exists (app.js's poll()).Reused EventSource, its own reconnect-on-drop handling, a second live-update code path next to the polling one that still runs the rest of the page.
Update granularity Learns about a finished step within 2–8s. Learns instantly — but the download itself only reports 4 checkpoints, so "instant" delivers the same 4 numbers, just sooner.
Cost per update One small request/response, ~40–60 of them over a typical download.Negligible One open socket for the whole download's duration, held by the server the entire time.
If the tab is backgrounded Loop already pauses on a hidden tab and resumes on return — built in. Connection either idles open (wasted) or the browser throttles it — needs its own handling either way.
Debuggability curl localhost:8000/api/prefetch — that's the whole surface.Simplest Needs an SSE-aware client or browser dev tools' network-stream view to inspect.
Failure recovery A dropped request just retries on the next tick — no special case.No special case A dropped connection needs explicit reconnect logic, or progress silently stops updating.

Does polling every 2s actually add up to "a lot of requests"?

Worked against a real download this size — run end-to-end while building this: 22 grammars (seconds), the BM25 tokenizer files (seconds), and the ~550 MB embedding model (~20s on this connection).

~45s
typical total download time
≈20
poll requests, at 2s while busy
~250 B
response size per poll
~5 KB
total traffic for the whole bar

Each poll is a dictionary read already sitting in memory — no disk, no database, no Qdrant round-trip. On a single-operator local dashboard this is not the "multiple requests = overkill" case that polling earns its bad reputation from; that reputation comes from polling a slow or rate-limited external API at high frequency from many clients, which this is not.

Why this isn't a fresh decision

Noesis already answered this question once, for index-run progress, and answered it with polling. This reuses that answer rather than re-opening it.

ctx.progress In-memory dict already tracking live progress for index runs — the new job reuses the identical shape (ctx.prefetch_job) instead of inventing a second kind of live state.
GET /runs/{'{'}run_id{'}'} The existing polled status endpoint for a running index — same pattern the new GET /api/prefetch follows.
app.js → poll() The dashboard's one polling loop, backing off 2s → 8s and pausing on a hidden tab — extended with one more condition rather than duplicated.
§4.12 design principle Server-rendered pages, no SPA tooling, no build step. Polling fits that directly; SSE would be the first long-lived connection anywhere in the codebase.

When SSE would actually be worth it

Not "never" — just not for this. It earns its cost when either is true:

Sub-second freshness genuinely matters — a live chat, a stock ticker, a collaborative cursor — where a 2s lag is visibly wrong, not just slightly stale. Or the underlying work reports far more granular progress than 4 checkpoints, so streaming would show something polling structurally can't. Model-prefetch progress is neither: it's an admin button clicked rarely, tracking a handful of coarse steps, on a dashboard nobody is staring at frame-by-frame.
