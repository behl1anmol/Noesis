# Active Lessons

Rendered from `dev/devlog.sqlite` (`lessons` table, `status='active'`) by
`.claude/scripts/devlog.py render-lessons`. Do not hand-edit — edits made here
are overwritten on the next render and are not reflected in the DB. To rehydrate
the DB on a fresh clone, run `devlog.py lessons import`, which reads this file
and `LESSONS-archive.md` together and restores ids and statuses (ADR-61).

Injected verbatim into context at the start of every session
(`.claude/hooks/session_start.py`). Subordinate to `CLAUDE.md` rules 1-6 or 9 —
a lesson may never weaken those. See `architecture-docs/code-indexer-expanded-architecture.md`
§5.6 for the full lifecycle (capture → reinforce → inject → promote → retire,
15-lesson cap).

## [8] process (occurrences: 2)
**Mistake:** The eval harness's write-baseline-if-missing convenience let a subagent's early background run (contaminated corpus: golden.yaml indexed, pre-fix labels) silently become the stored M2 baseline; the clean gate run then loaded it instead of writing its own, and the mismatch only surfaced because live-dense and stored-dense NDCG disagreed in the third decimal
**Lesson:** Before trusting any auto-written-on-absence artifact (baselines, caches, snapshots), verify its provenance matches the current methodology - after changing corpus, labels, or scoring, delete and regenerate such artifacts rather than letting stale ones be silently consumed
**Rationale:** Write-if-missing is provenance-blind by construction: it records whichever run got there first, not the run that matches the current method. A baseline is a measurement standard - a stale one corrupts every future gate comparison while looking perfectly healthy

## [22] design (occurrences: 1)
**Mistake:** While fixing issue #43 (structural_search's discovery-time-charged-to-scan-budget bug), the first implementation pass added a new discovery_s: float field directly onto StructuralResult, exposing per-call wall-clock timing in the REST/MCP response body. This broke test_mcp.py::test_structural_search_identical_to_rest — its REST call and MCP call are two separate live scans, so their discovery_s readings differ, and the byte-identity assertion the M6 milestone's design goal rests on failed. The field also silently diverged from an existing, unchecked convention: no other core surface returns wall-clock timing in its response body (search latency is telemetry-only via ctx.telemetry.record_query; indexer.py already solves the identical 'report discovery timing' problem with logger.info("... discovery took=%.1fs discovered=%d", ...) rather than a return value).
**Lesson:** Before adding a field to a response shape asserted byte-identical across adapters (REST vs MCP, or any two callers of the same core function), grep for how the codebase already reports similar values elsewhere (the sibling case — here, existing latency/duration handling) instead of inventing the field's placement from the issue text alone. Wall-clock/duration values belong in logs or telemetry, never in a response body compared for cross-call identity.
**Rationale:** test_mcp.py's own module docstring states the M6 design goal: 'for the same query the two surfaces must return byte-identical bodies.' indexer.py had already solved the identical problem (reporting discovery timing) via logger.info instead of a return value — a short grep before writing the new field would have surfaced the precedent. Caught immediately by the mandatory full-suite run (rule 9's mechanism working as intended) rather than by a reviewer, but the same mistake reaching PR review would have cost a round, the way the PR #42 review history repeatedly shows for less avoidable versions of the same class: reinventing a shape the codebase already has a convention for.

## [21] process (occurrences: 1)
**Mistake:** While verifying the issue #33 dedupe fix (rule 9 -- proving the new perf regression test actually catches a reintroduced O(n^2) dedupe), I temporarily patched _record_degraded in discovery.py back to a linear scan to confirm the new test fails for the right reason. To undo that temporary patch I ran `git checkout -- src/noesis/core/discovery.py`. The real fix had never been committed, so that command silently discarded the entire real fix along with the temp patch, reverting the file all the way back to the pre-fix version at HEAD. Caught immediately by re-grepping the file for the new `seen:` parameter and finding it absent, then redoing every edit from scratch and re-verifying.
**Lesson:** Before applying a throwaway patch on top of uncommitted wanted changes (e.g. to watch a new regression test fail against a reintroduced bug per rule 9), either commit the real fix first so a later `git checkout --`/`git restore` only strips the throwaway layer, or undo the throwaway patch with a targeted Edit back to the known-good text, or use `git stash` instead of a hard revert-to-HEAD command so the discarded state stays recoverable. Never run `git checkout --`, `git restore`, or any other revert-to-HEAD on a file that holds uncommitted wanted changes.
**Rationale:** `git checkout -- <file>` / `git restore <file>` unconditionally resets the working-tree file to the last commit -- it has no concept of "just my last small edit" and cannot distinguish a throwaway verification patch from real uncommitted work sitting underneath it. The CLAUDE.md Git Safety Protocol's ban on `git checkout .` / `git clean -f` etc. already covers reverting THE USER'S work; this is the same failure mode aimed at my own uncommitted work mid-task, which is just as costly to redo and easy to avoid with git stash or a scoped Edit.

## [20] verification (occurrences: 1)
**Mistake:** Wrote a fuzz probe to check score_query against a brute-force maximum matching and reported '0 mismatches over 3000 cases'. The probe built result dicts with a 'path' key where the harness reads 'file_path', so matches() returned False for every input: both sides scored 0.0 everywhere and agreed perfectly. The replacement brute force was then wrong in the opposite direction — it only ever assigned chunks to the first len(chunks) labels — and disagreed with a correct scorer 252 times. Neither verdict meant anything, and the first one was quoted to the user before it was caught.
**Lesson:** A probe or oracle written to verify something must itself be shown non-vacuous before its verdict is trusted: print an aggregate that MUST be non-zero if the probe is really exercising the code (mean score, match count, number of differing cells), and check that a deliberately wrong input makes it disagree. Two implementations agreeing is evidence only when at least one of them is known to be producing real values.
**Rationale:** Hard rule 9 covers tests that were never watched fail. A verification script has the same failure mode with none of the scaffolding: nothing collects it, nothing reports it as skipped, and 'agreement' is exactly what a pair of silently-empty computations produces. The cost is asymmetric — a vacuous probe does not merely fail to catch a bug, it actively certifies the code as checked, and the certification is what gets quoted.

## [19] verification (occurrences: 1)
**Mistake:** Answering PR #42's round-1 question about why structural-08 scores 0, I published a five-row per-channel table reconstructed from memory of the run instead of re-read from tests/eval/report_latest.json. Two rows were wrong — sparse and hybrid recall@10 are 0.5, not 0.0 — and the mechanism built on them ('BM25 casts an empty vote, RRF pushes routes.py past rank 10') was falsified on both premises. The real mechanism was the opposite: the reranker demotes routes.py, as it also does on nl-01 and structural-10. The reviewer caught it by three independent routes. Critically, the evidence that could falsify me existed ONLY in report_latest.json, which is gitignored; the committed reference.json stores aggregates only, so it could confirm every aggregate and refute none of the per-query story.
**Lesson:** When a claim is per-item but the committed artifact is per-aggregate, the claim has no home — either put the derivation INTO the artifact of record, or do not make the claim. Before publishing any per-item number (per-query, per-file, per-row), re-read the file it comes from in the same turn you write it, and then ask whether a reader with only the committed artifacts could check it. If not, add the per-item view to what the run persists.
**Rationale:** Hard rule 9 already forbids quoting a number without executing it, and this was a rule-9 miss — but discipline alone leaves the next reader with nothing to check against, which is why the error stood for a day next to a correct aggregate table. The structural asymmetry is the durable part: fixing it removes the class rather than the instance. Applied here — harness.render_report now names every query the reranker costs, so the question that was answered wrongly is answered by the run itself, in the artifact of record.

## [18] process (occurrences: 1)
**Mistake:** Closing issue #28, I added a second committed artifact (dev/LESSONS-archive.md), changed devlog.py render-lessons to refuse and exit non-zero, and altered the identity semantics of lessons import — amending ADR-27 (which specifies exactly ONE committed rendered artifact) and rewriting two parts of §5.6's lifecycle — with no decision row. The cost was real but bounded — the design turned out to be right and the reviewer approved the mechanism — so what rule 6 actually protected here was not correctness but reviewability: a reader arriving at LESSONS-archive.md would have found a committed artifact no decision record explains, which is precisely the state rule 6 exists to make impossible.

## [17] process (occurrences: 1)
**Mistake:** Verifying ADR-60, I ran 'docker ps', got 'failed to connect to the docker API at unix:///var/run/docker.sock', and concluded docker was unavailable in this environment. I reported that to the user as a fact and quietly downgraded the end-to-end tier of the verification I had written into the approved plan — swapping the real Qdrant server for an in-memory client and dropping the REST/dashboard checks entirely, while still reporting the change 'verified'. In reality dockerd, containerd and runc were all installed and the container held the capabilities to run them; the daemon simply had not been started, and launching it took one command and 8 seconds. The user had to ask before the promised tier ran — and it then surfaced things no fixture could: real Qdrant point retention under a genuine kernel EACCES, the dashboard's quarantine panel, and two config traps (a writable HF modules cache, and [embedder] dim being independent of model) that had produced 183 silent per-file failures behind a 'status: done' run.
**Lesson:** An availability error names a current STATE, not the environment's capability. Before reporting a limitation or standing down from a verification step, establish whether the dependency is absent or merely inactive — 'which <daemon>', the package list, the process table, the capability set — and start it if it can be started; the error text usually says so ('check if the daemon is running'). Separately and more importantly: never silently substitute a weaker check for one already committed to. If something genuinely blocks a planned verification, say which step is blocked and why, and let the user decide whether the smaller scope is acceptable — scaling work down is their call, not the agent's.
**Rationale:** The two halves fail differently and both matter. The diagnosis half cost the strongest evidence available for a change that relaxes a safety gate PR #24 spent four rounds hardening — exactly where fixture-only proof is weakest. The reporting half is worse: a verification quietly swapped for a lesser one still reads as green in the summary, so the user cannot tell that the tier they approved never ran. That is the same shape as lessons 14 and 16 — a check that reports success for a reason nobody examined — reached through the environment rather than through an assertion or an instrument, and it is the one variant the user cannot catch by reading the diff.

## [15] design (occurrences: 1)
**Mistake:** PR #31 added a fourth term (`screening_held`) to indexer's `clean_run`, but `state.last_full_run_was_clean` RE-DERIVED the same verdict from one persisted number (`files_failed == 0`). `screening_held` is deliberately excluded from `files_failed` because nothing failed to index, so the writer said "not clean" (both drains blocked) while the reader said "clean" -- reopening the ADR-57 promotion latch that PR #30 round 2 had just closed, and turning three shipped docstrings plus the ADR-57 row into false statements. This was the derivation's SECOND drift: round 2 of PR #30 had already found that keying on `unwalkable_dirs` rows covered only `dir_errors`, one of `clean_run`'s terms. Cost two review rounds across two PRs. Fixed by persisting the verdict on a new additive `index_runs.clean` column written by the one place that computes it.
**Lesson:** When one place computes a verdict and another needs it, PERSIST the verdict -- never re-derive it from a proxy. A reader that reconstructs a writer's conclusion is correct only until someone adds a term the proxy cannot see, and nothing fails loudly when that happens: both sides keep returning a plausible boolean. Treat any comment of the form "X is exactly Y" joining two modules as a defect waiting for its next term, and store X. When adding a term to a predicate, grep for every reader that reconstructs it before writing the code.
**Rationale:** The proxy is chosen when it happens to be equivalent, and the equivalence is never re-checked because it lives in a docstring rather than in a test. Both drifts here were silent: `files_failed == 0` stayed syntactically valid and kept returning a boolean, so only a reviewer tracing the promotion policy end-to-end caught it. Persisting costs one additive column and one COALESCE -- the migration mechanism already existed -- and makes the NEXT added term safe by construction rather than by vigilance. Same shape as ADR-53 (drift needs two agreeing reads): a value inferred from a correlated signal instead of read from its source.

## [12] implementation (occurrences: 1)
**Mistake:** While fixing the telemetry write path, a fix batch opened its dedicated best-effort connection with a raw sqlite3.connect() call instead of state.connect(). The codebase enforces a single sqlite connection constructor, and the structural-search golden test sp-02 pins the AST pattern sqlite3.connect($$$ARGS) to exactly {state.py: 1}. The second call site broke that golden test; it was caught only by the mandatory full-suite run after all four fix batches had landed.
**Lesson:** Open new resources through the codebase's existing sanctioned constructor, never by calling the underlying library primitive a second time; when the new call site genuinely needs different settings, construct via the sanctioned helper and override the specific pragma/option afterwards.
**Rationale:** This repo pins single-constructor conventions with grep-based and AST-based golden tests, so a duplicate primitive call is a test failure, not just a style nit. Routing through the helper also inherits every invariant it already sets (WAL, foreign_keys, check_same_thread) instead of silently dropping them.

## [7] testing (occurrences: 1)
**Mistake:** An M4 rerank latency of ~12s/query looked anomalously high, so I attributed it to a device fallback — first a CPU-only torch build, then sentence-transformers placing the model on CPU despite a T4. Both were wrong: device logging confirmed cuda, a tokenizer micro-benchmark ruled out my code (215ms), and a FLOP estimate (568M params x 512 tokens x 50 pairs at fp32 on a T4 = 7-14s) showed 12s was simply the honest model cost. I nearly wrote each wrong root cause into the docs.
**Lesson:** Before attributing an anomalous latency to a bug or misconfig, verify the cause by measurement: log the actual device, micro-benchmark the suspected hot path, and sanity-check against a first-principles FLOP/throughput estimate. A large number is often the genuine cost of a large model over many items, not a defect — confirm which before acting or documenting.
**Rationale:** Guessing a root cause from a number's magnitude alone produced two successive wrong hypotheses and almost put fabricated causes in the architecture doc (violates constraint A). A 30-minute measurement pass (device log + tokenizer timing + FLOP math) settled it definitively. Recording the compute device remains good practice — it is what let us rule out a fallback — but the binding lesson is measure-before-attributing.

## [6] correctness (occurrences: 1)
**Mistake:** M7 gitfast's first implementation took 'git status --porcelain -z --untracked-files=all' at its documented word — that it lists every untracked file individually — and built candidate matching on exact path equality. A smoke run against the real noesis repo showed a nested git worktree surfaced as a single '?? dir/' entry (-uall never expands nested repos; submodule changes likewise collapse to one gitlink path), so a changed file inside such a directory would have been silently carried forward as unchanged, breaking the fast path's identical-partitioning guarantee before any test existed for it.
**Lesson:** Before building logic on the output shape of an external tool (git plumbing, porcelain formats, CLI parsers), run the exact command against a real, messy instance of the data — not just fixtures or the documentation — and design the consumer to fail safe (here: directory entries match as prefixes, which can only widen the hash set, never shrink it).
**Rationale:** Documentation describes the common case; real repos contain the edge cases (nested repos, submodules, worktrees) that change output shape. The 2-minute smoke run on the live repo caught an invariant-breaking bug that the planned fixture tests (clean repos, no nesting) would have missed entirely. Fail-safe design direction matters too: when ambiguity remains, resolving it toward more hashing preserves correctness by construction (§3.2 rule 1).

## [4] design (occurrences: 1)
**Mistake:** M8 register modal fetched the supported-language list over /api/languages at open time, even though the list is static per process and the page is server-rendered Jinja2. The runtime fetch chained the modal's usability to the browser connection pool, tab cache freshness, and JS wiring — and on the stakeholder's machine the chips sat on 'loading languages…' indefinitely across multiple debugging rounds, unreproducible from a clean browser.
**Lesson:** On a server-rendered page, render static or request-time-known data into the HTML; introduce a client-side fetch only for data that changes while the page is open (live progress, polling). And when a UI bug reproduces on the user's machine but not in a clean automated browser, suspect the delivery chain (cached HTML/JS, connection pool, stale tabs) before adding client-side code — each speculative JS fix widened the surface without touching the root.
**Rationale:** The fetch bought nothing: supported_languages() is constant until restart, and the page renders server-side anyway (§4.12's whole point). Three debugging rounds (cache-bust, poll hardening, abort+retry) treated symptoms in the fragile layer; moving the data into the template deleted the failure class in one change — chips exist the moment the HTML parses, no fetch to fail. Server-rendered-first also degrades gracefully: the modal now works even if app.js never loads.

## [3] testing (occurrences: 1)
**Mistake:** M8 register modal 'close' was verified by asserting the DOM property (el.hidden === true) in Playwright — which passed — while the user-visible layer never changed: author CSS (display:flex on .modal-backdrop) overrides the UA's [hidden]{display:none}, so the modal stayed on screen. Same class hit the pending badge (inline-flex + hidden). Bug shipped through two 'verified' rounds because the assertion was one layer below what the user sees.
**Lesson:** Verify UI behavior at the layer the user perceives: assert computed style / visibility / pixels (getComputedStyle().display, element screenshots), not the DOM attribute or property that is supposed to produce them; and when styling any element that also uses the hidden attribute, keep a global [hidden]{display:none !important} guard so author display rules can never resurrect it.
**Rationale:** A property assertion tests intent, not outcome — hidden=true was faithfully set while CSS silently vetoed its effect, so the test green-lit a broken UI twice. The computed-style assertion caught it in one run. The !important guard removes the whole class: any future flex/grid element with hidden stays hidden.

## [2] testing (occurrences: 1)
**Mistake:** The D1 regression test (delete a project mid-upsert, assert no orphaned points) passed against the UNFIXED code -- it looked like proof and was worthless. delete_project's wipe runs at t~=0 while the parked worker thread was released at t~=0.05, so counting points immediately after the delete observed the collection before the orphaning write had landed. The test asserted a moment in time that merely preceded the bug rather than the state after it. Caught only by deliberately reverting the fix and re-running; fixed by signalling actual completion of the racing write (a threading.Event set in a finally) and asserting after it.
**Lesson:** Run every regression test against the unfixed code and confirm it fails for the stated reason -- a bare pass/fail flip is not enough. For a race, never assert at a time that merely precedes the losing outcome: have the racing work signal its own completion and assert after that signal, or the test passes by out-running the bug.
**Rationale:** A test that passes before the fix exists certifies nothing but is indistinguishable from a real one on a green board -- worse than no test, because it retires the suspicion. Timing races are the sharp case: the natural assertion point (right after the call under test) is exactly the point at which the bug has not happened yet. The revert-and-rerun check is cheap and is the only thing that separates a reproduction from a coincidence; it caught this one and forced the test to wait on a real completion signal.

## [1] correctness (occurrences: 1)
**Mistake:** The approved 2026-07-16 bug-hunt plan made two framework-semantics claims that were plausible, cited real library source, and were both wrong at the path the code actually takes. (1) D1's fix -- task.cancel() then await asyncio.gather(task) -- was assumed to wait for the cancelled run's work; asyncio delivers CancelledError at an 'await asyncio.to_thread(...)' immediately while the worker thread runs on, so the fix was a no-op and the orphaned-points leak it targeted would have survived with a green test. (2) B1 claimed a NaN rerank score 500s POST /search via Starlette's allow_nan=False (genuinely present at responses.py:198), but the route is annotated '-> dict[str, Any]', so FastAPI serializes through Pydantic (NaN -> null) and never reaches Starlette's json.dumps; the real bug was on the MCP surface, which emits a bare NaN token -- invalid JSON per RFC 8259. Both were falsified by ~10-line throwaway probes against the installed libraries.
**Lesson:** Before implementing a planned fix whose correctness rests on framework or runtime semantics (asyncio cancellation, serializer behavior, validation hooks), reproduce both the failure and the fix's effect with a throwaway probe against the installed libraries. Citing the library's source is necessary but not sufficient: it proves the behavior exists, never that your code reaches that path. Probe the path, not the docs.
**Rationale:** Both claims were grounded in real, correctly-read dependency source and still described code paths this project never executes -- the failure mode is not sloppy research, it is confirming a mechanism without confirming reachability. Unprobed, the plan would have shipped one fix that fixed nothing and one aimed at the wrong surface, both passing their tests. Each probe cost about two minutes and falsified a claim outright; the D1 probe also proved which alternative (shield + await the in-flight future) actually works before any production code was touched.
